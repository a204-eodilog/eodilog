# 폰 안 사진 AI

**결론: 사진 주제 분류와 한국어 문장 사진 검색을 폰 안에서 한다. 폰용 모델(191MB)은 평가 사진 1,931장에서 분류 97.4%로, 지금 서버 분류기(96.6%)보다 높다. 검색은 정답 사진이 5위 안에 나오는 비율이 52.1%에서 77.7~78.5%가 됐다.** 사진은 분석하려고 서버로 보내지 않는다. 2019년 폰(Galaxy S10 5G)에서 사진 한 장 0.30초, 검색어 하나 0.14~0.38초다.

## 왜 폰에서 하나

- 개인정보: 여행 사진에는 얼굴, 위치, 영수증이 담긴다. 분석을 위해 서버로 보낼 필요가 없다.
- 밖에는 와이파이가 없다: 찍은 자리에서 인터넷 없이 바로 나누고 찾는다.
- 전송 비용과 시간: 원본 50장(4,000px)은 약 118MB다(§`photo-classification-eval.md` 14). 폰에서 하면 분석 때문에 나가는 데이터는 0이다.

## 결과 (평가 사진 1,931장, 학습에 쓰지 않음)

| 지표 | 학습 전 | 폰용 최종 | 비교 |
| --- | --- | --- | --- |
| 주제 분류 정확도 | 74.6% (원본 모델 + 첫 버전 주제 문장) | **97.4%** | 서버 분류기 96.6%, 큰 선생 97.8% |
| 문장 검색, 정답이 5위 안 | 52.1% | **77.7~78.5%** | 검색 선생(SO400M) 78.5% |
| 문장 검색, 정답이 1위 | 27.3% | 47.4% | |
| 메뉴판 301장(기타) | 59.1% (고친 주제 문장) | 99.7% | 첫 버전 문장 95.0% |
| 실내·바깥 30장 | 66.7% (첫 버전 문장) | 100% | |

- 정답 주제는 GMS가 두 번 판단해 일치한 것이다(사람 검토 아님).
- 학습 전후 사진 비교와 화면 자료는 `ai/presentation/`(로컬, 커밋하지 않음)에 있다.

## 만든 방법

1. 큰 선생 모델(SigLIP2 SO400M, 사진+문장 약 4.3GB)을 분류와 한국어 설명 검색으로 학습했다.
2. 폰 크기 모델(SigLIP2 B-32)이 선생의 분류 판단과 문장-사진 유사도를 따라 하도록 함께 학습했다(`scripts/ondevice/joint.py`).
3. 사진 모델은 8비트 흉내 학습 뒤 int8로, 문장 모델은 단어표를 21,975개로 줄인 뒤 4비트로 바꿨다. 크기 1,438MB → 191MB, 성능은 그대로다.
4. H200에서 실험 308번, 학습 시간 38.6 GPU시간(데이터 불러오기·평가 제외, 11/13 21시 기준).

| 단계 | 크기 | 분류 | 검색 5위 안 |
| --- | --- | --- | --- |
| 큰 선생 SO400M | 4,334MB | 97.77% | 78.5% |
| B-32 학습 후, 줄이기 전 | 1,438MB | 97.31% | 79.0% |
| 폰용 최종 (사진 int8 + 문장 4비트) | 191MB | 97.41% | 78.5% |

## 비슷한 사진 묶기 기준값

폰용 사진 모델로 다시 맞췄다(`scripts/ondevice/calibrate_group.py`, 결과 `ondevice-group-calibration.json`). 같은 사진 쌍은 평가 사진마다 연속 촬영처럼 바꾼 사본(5~12% 잘라내기, 밝기 ±12%, JPEG 60~85, 작은 이동), 다른 사진 쌍은 평가 사진끼리 1,862,415쌍이다.

| 기준값 | 같은 사진을 묶는 비율 | 다른 사진이 잘못 묶인 쌍 |
| --- | --- | --- |
| 0.90 | 99.7% | 300쌍 (1.6/1만) |
| **0.92 (앱에 씀)** | **99.1%** | **86쌍 (0.46/1만)** |
| 0.94 | 93.8% | 15쌍 |

- 평가 사진 안에 같은 사진이 두 번 들어 있는 경우가 있어(최고 유사도 1.0) 잘못 묶인 쌍 수는 실제보다 크게 잡힌다.
- 앱은 닮은 사진을 사슬로 잇기 때문에(A~B, B~C면 한 묶음) 쌍 기준보다 묶음이 조금 커질 수 있다. 실제 연속 촬영 사진으로는 아직 재지 않았다.

## 앱과 서버 연결

- 앱(사진 올리기 S30): 여행 기간에 찍은 내 폰 사진을 폰에서 정리한다(주제, 비슷한 사진, 문장 검색). 골라 담아 올리면, 올린 사진의 결과만 서버로 보낸다.
- 앱(여행 사진 S31): 서버에 저장된 비슷한 사진 묶음을 대표 한 장 + '+n'으로 접어 보여 주고, 누르면 펼친다.
- 앱(마이페이지 → 내 사진 찾기): 내 모든 여행 기간에 찍은 폰 사진을 여행별 칩으로 나눠 문장으로 찾는다.
- 설정에서 AI 사진 분류를 끈 사용자(OFF)는 폰 정리를 시작하지 않는다. 모델이 없고 모바일 데이터면 받기 전에 묻는다. '일부 사진만 허용'이면 허용한 사진만 정리한다고 알린다.
- 백엔드: `POST /api/v1/trips/{tripId}/photo-classifications/device` (`docs/api-spec.md`). 내가 올린 사진만, 버전이 맞을 때만, AI 사진 분류를 끄지 않았을 때만 적용한다. 같은 묶음 키를 2장 이상 쓰면 서버가 새 묶음을 만든다.
- AI 서버의 `/ai/v1/photo-classifications`는 쓰지 않게 된다. 예비로 둔다.

## 폰 실측 (2026-11-16)

Galaxy S10 5G(2019년, 안드로이드 12), 사진실험 앱 release 빌드, 측정은 앱의 `ONDEV_RESULT` 로그.

| 항목 | 결과 |
| --- | --- |
| 모델 받기(처음 한 번, 4개 약 200MB) | 약 6초(USB로 노트북에서 받음) |
| 모델 열기 | 1.3~1.4초 |
| 처음 정리 409장(대부분 1,000~2,500px) | 124초, 장당 0.30초 |
| 다시 열기 414장(저장한 결과 사용) | 0.1초 |
| 검색어 하나(16번) | 0.14~0.38초 |
| 비행기 모드 | 새로 찍은 사진 분류와 검색 모두 됨 |

- 테스트 사진 405장은 제주 메뉴판 301장과 풍경·음식·사람 등 104장이다. 바다·회 사진이 거의 없어 '해운대에서 먹은 회'는 음식·메뉴판이 나왔다. 노트북에서 같은 모델로 돌려도 같았다.
- 검색은 처음에 비슷한 순서로 60장을 채워 '바다'에 메뉴판이 섞였다. 앱은 1위 점수의 75%보다 낮은 사진을 빼도록 고쳤다(바다 사진만 남음). 75%는 이 사진들로 정한 값이라 실제 여행 앨범으로 다시 확인해야 한다.
- 배터리와 4,000px 원본 사진의 장당 시간은 아직 재지 않았다.

## 참고: 작은 CNN

사진 모델만 5~15MB CNN으로 바꾸는 실험도 했다(`scripts/ondevice/cnn_emb.py`). 분류는 거의 따라오지만(EfficientNet-B0 5M 97.0%), 검색은 최고 61.3%(ConvNeXt-nano)로 B-32(79.5%)보다 많이 낮아 쓰지 않는다. 분류만 폰에서 할 때의 대안이다.

## 남은 일

- 폰 배터리 소모와 4,000px 원본 사진의 장당 시간.
- 검색 결과를 자르는 비율(75%)을 실제 여행 앨범으로 확인.
- 실제 연속 촬영 사진으로 묶기 기준값 확인.
- 모델 파일을 둘 곳 정하기.
