# Git 커밋·브랜치 컨벤션

## Git-flow 브랜치 전략

Git-flow의 상시 브랜치와 작업·배포·긴급 수정 브랜치를 구분한다. 원형의 `develop` 역할은 이 저장소의 **`dev`**가 맡는다. 배포 기준은 **`master`**다. 설명을 위해 기존 브랜치를 일괄 변경하거나 `develop`을 추가하지 않는다.

기준: [Vincent Driessen의 Git-flow 원문](https://nvie.com/posts/a-successful-git-branching-model/). 아래의 이슈 기반 이름, 문서·설정 접두사와 GitLab MR 절차는 이 저장소에 적용하는 운영 규칙이다.

### 브랜치 역할과 분기·병합 대상

| 브랜치 | 역할 | 생성 기준 | 병합 대상 |
| --- | --- | --- | --- |
| `master` | 배포 가능한 버전 보관, 배포 버전 태그 부여 | 상시 유지 | 배포·긴급 수정 결과를 받음 |
| `dev` | 다음 배포를 위한 개발 결과 통합 | 상시 유지 | 작업·배포·긴급 수정 결과를 받음 |
| `feature/<이슈키>-<작업명>` | 기능 개발·일반 버그 수정 | 최신 `dev` | `dev` |
| `docs/<이슈키>-<작업명>` | PRD·API 명세 등 문서 작업 | 최신 `dev` | `dev` |
| `chore/<이슈키>-<작업명>` | 설정·빌드·개발 도구 정비 | 최신 `dev` | `dev` |
| `release/<버전>` | 배포 준비·검증·배포 전 오류 수정 | 배포할 기능이 모인 `dev` | `master`와 `dev` |
| `hotfix/<버전>` | 이미 배포한 버전의 긴급 장애 수정 | 배포 기준 `master` | `master`와 `dev` 또는 진행 중인 `release` |

`docs`·`chore`는 작업 성격을 구분한 것으로, Git-flow의 기능 작업 브랜치와 같은 생명주기를 따른다. 개발 중 발견한 일반 버그는 작업 브랜치에서 처리하고, 배포 장애를 긴급 수정할 때만 `hotfix`를 사용한다.

### 브랜치 이름

- 작업 브랜치는 **하나의 이슈·목적**으로 묶는다. 커밋마다 새 브랜치를 만들지 않는다.
- 이슈키는 실제 할당된 Jira 키를 사용하고 임의로 만들지 않는다. 작업명은 소문자 영문과 하이픈으로 쓴다.
- 예시 형식: `feature/EODI-NNN-trip-vote`, `docs/EODI-NNN-prd-update`. `NNN`은 실제 이슈 번호로 바꾼다.
- 배포·긴급 수정은 `release/1.0.0`, `hotfix/1.0.1`처럼 버전을 쓴다. 배포 태그는 `v1.0.0`처럼 붙인다.
- 기존 `feat/...` 등 브랜치는 작업 중 임의로 이름을 바꾸지 않는다. 새 작업부터 위 형식을 적용한다.

### 일반 작업 순서

1. 현재 브랜치·미커밋 변경·담당 이슈를 확인한다. 같은 이슈의 미병합 작업 브랜치가 있으면 그 브랜치에서 이어간다.
2. 새 작업이라면 최신 원격 `dev`에서 작업 브랜치를 만든다. 다른 사람의 작업 브랜치나 오래된 로컬 브랜치에서 분기하지 않는다.
3. 해당 작업 파일만 선택해 커밋하고 작업 브랜치로 푸시한다.
4. GitLab에서 **작업 브랜치 → `dev`** Merge Request(MR)를 생성한다. 변경 내용과 확인 결과를 적고 리뷰·필수 검사를 거쳐 병합한다.
5. 병합 완료를 확인한 뒤 작업 브랜치를 삭제한다. 이미 병합된 브랜치는 새 작업에 재사용하지 않는다.

다음은 새 문서 작업의 명령 예시다. 미커밋 변경이 있으면 먼저 보존 방법을 정하고, 경로와 이슈키를 실제 작업에 맞게 바꾼다.

```powershell
git status
git fetch origin
git switch -c docs/EODI-NNN-prd-update origin/dev

# 문서 수정 후 해당 파일만 추가
git add -- path/to/document.md
git diff --cached
git commit -m "Docs : PRD 정책 변경 반영"
git push -u origin docs/EODI-NNN-prd-update

# GitLab에서 source: 작업 브랜치, target: dev로 MR 생성
```

### 배포 준비와 완료

1. 배포할 작업을 `dev`에 모은 후 `origin/dev`에서 `release/<버전>`을 만든다.
2. 배포 브랜치에서는 버전·배포 설정·검증과 오류 수정만 한다. 새 기능은 작업 브랜치를 통해 `dev`로 보낸다.
3. 검증이 끝나면 **`release → master`** MR을 병합하고, 병합된 배포 커밋에 버전 태그를 붙인다.
4. **동일한 배포 브랜치를 `dev`에도 병합**해 배포 준비 중 수정한 내용을 되돌려 반영한다. `dev` 전체를 `master`로 병합하면 다음 배포용 변경까지 포함될 수 있으므로 대체하지 않는다.
5. 태그와 두 병합이 모두 반영됐는지 확인한 뒤 배포 브랜치를 삭제한다.

```powershell
git fetch origin
git switch -c release/1.0.0 origin/dev
# 검증 후 GitLab에서 release/1.0.0 → master, dev 각각 MR 진행
# master 병합 후 해당 배포 커밋에 v1.0.0 태그 부여
```

### 배포 장애 긴급 수정

1. 최신 배포 기준 `origin/master`에서 `hotfix/<패치버전>`을 만든다.
2. 장애 수정·버전 갱신·검증을 마치면 **`hotfix → master`** MR을 병합하고 패치 태그를 붙인다.
3. 진행 중인 배포 브랜치가 없다면 **`hotfix → dev`**도 병합한다.
4. 진행 중인 `release`가 있다면 **그 배포 브랜치에도 수정 사항을 병합**한다. 이후 `release → dev`로 반영한다. 그 전에 `dev`에도 수정이 필요하면 직접 반영하되 중복·충돌을 확인한다.
5. 필요한 병합과 태그 반영을 확인한 뒤 긴급 수정 브랜치를 삭제한다.

```powershell
git fetch origin
git switch -c hotfix/1.0.1 origin/master
# 검증 후 master 및 dev 또는 진행 중인 release에 MR 진행
```

### 병합·공유 원칙

- `master`·`dev`에 직접 커밋·푸시하지 않고 MR로 반영한다. 보호 브랜치 설정과 승인 인원은 GitLab에서 팀이 별도로 설정한다.
- 원형 Git-flow처럼 작업 단위 이력이 남도록 **merge commit 방식(`--no-ff`에 해당)**을 사용한다. Squash와 fast-forward만 사용하는 병합은 기본 방식으로 삼지 않는다.
- 작업 중 `dev` 변경이 필요하면 원격을 갱신하고 `origin/dev`를 작업 브랜치에 병합한다. 공유 브랜치 이력을 임의로 재작성하거나 강제 푸시하지 않는다.
- 푸시 전 브랜치와 스테이징 파일을 확인한다. `.env` 등 비밀정보를 포함하지 않는다.
- **AI 도구는 사용자가 명시적으로 지시한 경우에만 커밋·푸시한다.** 문서 수정 요청만으로 커밋·푸시를 실행하지 않는다. 브랜치 생성·변경·삭제도 명시적으로 요청받은 범위에서 수행한다.

## Commit 메시지 구조

기본적인 커밋 메시지 구조는 제목, 본문, 꼬리말 세 가지 파트로 나누고, 각 파트는 빈 줄을 두어 구분한다.

```
type : subject

body

footer
```

## Type

타입은 태그와 제목으로 구성되고, 태그는 영어로 쓰되 첫 문자는 대문자로 한다.

`태그 : 제목`의 형태이며, `:` 뒤에만 space가 있음에 유의한다.

```
feat : 새로운 기능 추가
fix : 버그 수정
docs : 문서 수정
style : 코드 포맷팅, 세미콜론 누락, 코드 변경이 없는 경우
refactor : 코드 리펙토링
test : 테스트 코드, 리펙토링 테스트 코드 추가
chore : 빌드 업무 수정, 패키지 매니저 수정
config : 설정사항 수정
```

## Subject

제목은 최대 50글자가 넘지 않도록 하고 마침표 및 특수기호는 사용하지 않는다. 영문으로 표기하는 경우 동사(원형)를 가장 앞에 두고 첫 글자는 대문자로 표기한다. (과거 시제를 사용하지 않는다.) 제목은 개조식 구문으로 작성한다. → 완전한 서술형 문장이 아니라, 간결하고 요점적인 서술을 의미한다.

```
* Fixed --> Fix
* Added --> Add
* Modified --> Modify
```

## Body

본문은 다음의 규칙을 지킨다.

- 본문 내용은 양에 구애받지 않고 최대한 상세히 작성한다.
- 본문 내용은 어떻게 변경했는지보다 무엇을 변경했는지 또는 왜 변경했는지를 설명한다.

## Footer

footer는 optional이고 이슈 트래커 ID를 작성한다.

- `유형: #이슈 번호` 형식으로 사용한다.
- 여러 개의 이슈 번호를 적을 때는 쉼표(,)로 구분한다.
- 이슈 트래커 유형은 다음 중 하나를 사용한다.
  - `Fixes`: 이슈 수정 중 (아직 해결되지 않은 경우)
  - `Resolves`: 이슈를 해결했을 때 사용
  - `Ref`: 참고할 이슈가 있을 때 사용
  - `Related to`: 해당 커밋에 관련된 이슈 번호 (아직 해결되지 않은 경우)

```
Fixes: #45
Related to: #34, #23
```

## 커밋 예시

```
Feat: "회원 가입 기능 구현"

SMS, 이메일 중복확인 API 개발

Resolves: #123
Ref: #456
Related to: #48, #45
```
