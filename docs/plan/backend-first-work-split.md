# 백엔드 2인 첫 작업 분담안

작성일: 2026-10-28 · 상태: 작업 분담 제안

목적은 전체 기능을 반씩 배분하는 것이 아니라, **두 사람이 서로의 구현을 기다리지 않고 시작할 첫 작업을 정하는 것**이다. A/B는 담당자 구분이며 실명 배정은 둘이 정한다. 이후 기능은 이번 작업이 연결된 뒤 배분한다.

기준: [API 명세](../api-spec.md), [논리 ERD](../erd.dbml), [백엔드 개발 규칙](../../EodiLog/AGENTS.md).
이 문서는 첫 구현 범위이며 전체 서비스의 기능을 축소하거나 API 명세를 변경하지 않는다.

## 1. 첫 작업 요약

| 담당 | 이번 작업 | 확인할 사용자 흐름 |
| --- | --- | --- |
| A — 인증·회원 | 카카오 로그인 1종, 사용자 생성/재로그인, 서비스 인증 토큰 발급·검증, 내 정보 조회 | 카카오로 로그인하고 내 정보를 확인한다 |
| B — 여행 기본 관리 | 여행 생성, 내 여행 목록, 여행 상세, 이름·기간·여행지 수정 | 인증된 사용자가 여행을 만들고 본인 여행을 관리한다 |

로그인 전체와 여행 전체를 맡는 것이 아니다. A는 카카오 1종, B는 초대·이탈·삭제를 제외한 기본 흐름까지만 구현한다. 작업량이 정확히 같다고 가정하지 않으며, 먼저 끝난 사람이 통합 검증이나 다음 작업을 맡는다.

## 2. A 담당 — 카카오 로그인·회원 기본

### 구현할 API

아래 경로는 `/api/v1` 이후 경로다. `{provider}`는 이번에는 `KAKAO`만 지원한다. 네이버를 가짜 성공 처리하지 않는다.

| Method | 경로 | 구현 범위 |
| --- | --- | --- |
| POST | `/auth/oauth/{provider}/authorization-requests` | 허용된 redirect 검사, 로그인 시작 컨텍스트와 연결된 state 생성, 인증 URL 반환 |
| POST | `/auth/oauth/{provider}/sessions` | 인가 코드 교환, state·redirect·시작 컨텍스트 검증, 사용자 식별/생성, 서비스 세션 발급 |
| GET | `/me` | 서비스 토큰으로 식별한 본인 정보만 조회 |

### 세부 작업과 소유 범위

- 카카오 제공자 사용자 ID로 계정을 식별한다. 이메일만 같다는 이유로 다른 계정을 합치지 않는다.
- 최초 로그인은 사용자와 소셜 계정 연결을 생성하고 재로그인은 같은 사용자를 반환한다.
- 발급한 서비스 토큰의 서명/유효성·만료를 검사하고 인증 객체에 `UUID userId`를 담는다.
- `OAuthAuthorization`, `OAuthExchange`, `Session`, `MyProfile` 응답 필드와 오류 형식은 API 명세를 따른다. 갱신 API를 이번에 제외하더라도 기존 `Session` DTO를 임의로 축소하지 않는다.
- `users`, `oauth_accounts`, `oauth_attempts`, `sessions`의 구현·마이그레이션을 맡는다.
- 카카오 통신을 어댑터로 분리해 정상/실패 응답을 테스트에서 대체할 수 있게 한다.
- 공급자 비밀키·서비스 토큰·개인정보를 로그나 저장소에 노출하지 않는다.

### 이번 작업에서 제외

네이버 로그인, 토큰 갱신/로그아웃 API, 프로필 수정, 탈퇴, 팔로우·검색·추천, 개인 즐겨찾기, 여행 권한 검사는 후속 작업이다. 초기 프로필 필수값과 인증 세부 중 API 명세의 미정 사항은 구현 전에 A가 정리해 공유한다.

### 완료 기준

- 정상 인가 코드로 로그인하고 서비스 토큰으로 `/me`를 조회할 수 있다.
- 같은 카카오 계정으로 두 번 로그인해도 사용자/소셜 연결이 중복되지 않는다.
- 잘못된 state·redirect·재사용한 인가 컨텍스트를 거부한다.
- 카카오 교환 실패 시 로그인 성공 응답이나 불완전한 사용자 자료를 남기지 않는다.
- 위조·만료·누락된 서비스 토큰으로 보호 API에 접근할 수 없다.
- 제공자 통신 대체 테스트와 실제 카카오 개발 앱 연동 확인을 구분해 기록한다. 실제 연동을 확인하지 않았으면 완료했다고 표시하지 않는다.

## 3. B 담당 — 여행 생성·조회·기본 수정

### 구현할 API

| Method | 경로 | 구현 범위 |
| --- | --- | --- |
| POST | `/trips` | 이름 필수, 기간·여행지 선택 입력으로 여행 생성 |
| GET | `/me/trips` | 현재 사용자의 ACTIVE 멤버십에 속한 여행 목록, 상태 필터·페이지 처리 |
| GET | `/trips/{tripId}` | ACTIVE 멤버만 여행 내부 상세 조회 |
| PATCH | `/trips/{tripId}` | 멤버가 이름·기간·여행지 수정, `expectedVersion` 검사 |

### 세부 작업과 소유 범위

- 생성자를 방장 ACTIVE 멤버로 등록한다. 클라이언트가 보낸 작성자 ID로 생성자를 정하지 않는다.
- `trips`, `trip_members`, `trip_destinations`의 구현·마이그레이션을 맡는다.
- 명세대로 **여행·방장 멤버십·여행 채팅방·빈 단일 코스를 한 트랜잭션으로 생성**한다. 생성용 `chat_rooms`, `chat_participants`, `itineraries` 초기화도 B가 맡는다. 채팅 메시지/코스 편집 기능까지 구현하는 뜻은 아니다.
- 공동 피드는 여행 생성 시 만들지 않는다.
- 멤버십 권한 검사를 여행 패키지 안에서 제공한다. 회원 엔티티나 인증 필터를 직접 수정하지 않는다.
- 인증 사용자 ID를 받아 필요한 회원 표시 정보는 A가 제공하는 조회 계약으로 얻는다. 테스트에서는 해당 조회를 대체한다.
- 여행지는 지역 ID로 연결한다. 지역 존재 확인 계약과 최소 테스트 자료만 준비하고 장소·지역 검색 API까지 확대하지 않는다.
- 기간 검증과 자동 상태 판정 규칙을 구현한다. 날짜 미정·시간대·시작/종료 경계는 구현 전에 공유해 맞춘다. 상태/통화를 임의로 수정하는 필드를 추가하지 않는다.
- 여행 정보 변경 이벤트를 발행하는 지점까지 준비한다. 알림 저장·전달은 후속 작업이다. 이벤트 발행만으로 명세의 변경 알림 기능까지 완료했다고 표시하지 않는다.

### 이번 작업에서 제외

초대 링크, 멤버 내보내기·방장 양도, 이탈·여행 삭제, 그룹 즐겨찾기, 투표, 코스 편집·AI·실시간 동기화, 채팅 메시지, 알림 전달, 사진·공동 피드·정산은 후속 작업이다.

### 완료 기준

- 이름만으로 여행을 만들고 생성자의 목록·상세에서 확인할 수 있다.
- 생성 후 방장 멤버십·채팅방/참여자·빈 코스가 존재하며 공동 피드는 없다.
- 초기화 일부가 실패하면 여행 생성 전체가 롤백된다.
- 비참여 사용자는 여행 내부 상세/수정을 할 수 없다. 존재를 공개할 수 없는 여행은 명세에 맞게 `404`로 처리한다.
- 날짜 역전 등 잘못된 입력을 거부하고 정상 이름·기간·여행지 변경을 저장한다.
- 오래된 `expectedVersion`으로 수정하면 `409 VERSION_CONFLICT`이며 다른 수정 내용을 덮어쓰지 않는다.
- 여행 생성의 `Idempotency-Key` 재시도에서 여행이 중복 생성되지 않는다.
- 목록의 ACTIVE 멤버 필터·정렬·커서를 검증한다. 회원 표시 정보에는 내부 개인정보를 포함하지 않는다.

## 4. 시작 전에 함께 맞출 최소 계약

| 항목 | 먼저 정할 내용 | 수정 책임 |
| --- | --- | --- |
| 사용자 식별 | 인증 객체에서 `UUID userId`를 얻는 호출 방식 | A가 인증 객체/접근 코드를 제공, B가 사용 |
| 회원 조회 | 여행 응답에 필요한 공개 회원 정보의 조회 인터페이스 | A가 실제 구현, B는 테스트 대체 구현 사용 |
| 여행 권한 | userId·tripId로 ACTIVE 멤버 확인하는 호출 방식 | B |
| 응답·예외 | API 명세의 성공/목록/오류 구조와 상태 코드 | 기반 작업 EODI-63과 정렬, 별도 공통 클래스를 둘이 중복 생성하지 않음 |
| 보안·환경 | 인증 공개 경로·보호 경로, DB 엔진/접속·영속화 방식 | 기반 작업 EODI-64와 정렬. A는 인증 변경, B는 여행 코드에서 사용 |
| DB 변경 | 테이블별 담당과 마이그레이션 파일명/번호 | 회원 A, 여행/생성 초기화 B. `regions` 공통 자료는 한 명이 관리 |
| 공통 파일 | `build.gradle`, `application*.yaml`, Security 설정, 공통 오류 코드 | 변경 전에 공유하고 파일별 한 명이 반영 |

기반 작업의 현재 상태를 먼저 확인한다. 이미 올라온 구현을 재사용하고, 없는 부분은 담당을 정해 한 번만 만든다.

**B는 A의 카카오 연동이 끝날 때까지 기다리지 않는다.** 테스트에서만 `UUID userId`가 담긴 인증 객체와 회원 조회 결과를 넣어 여행 흐름을 검증한다. 운영 코드에 임의 사용자 ID 헤더나 인증 우회 경로를 넣지 않는다. 실제 인증과의 결합은 이후 통합 검증에서 확인한다.

## 5. 첫 통합 검증

1. A의 카카오 로그인으로 서비스 토큰과 사용자 ID를 얻는다.
2. 그 토큰으로 B의 여행 생성 API를 호출한다.
3. 생성한 여행이 같은 사용자의 목록·상세에 표시되고 생성자가 방장인지 확인한다.
4. 같은 사용자가 이름·기간을 수정한다.
5. 다른 사용자 토큰은 해당 여행의 내부 조회·수정에 실패하는지 확인한다.

각 담당은 본인 범위 테스트와 Swagger 문서화를 포함한다. [백엔드 규칙](../../EodiLog/AGENTS.md)에 따라 `EodiLog`에서 `.\gradlew.bat build`를 통과시키고 `/v3/api-docs`의 경로·DTO·인증 표시도 검증한다.

## 6. 이번에는 배분하지 않는 후속 작업

팔로우, 개인/그룹 즐겨찾기, 초대·이탈·삭제, 투표·코스, 사진·평가·공동 피드, 정산, 그룹 채팅·알림은 첫 통합 뒤 배분한다. 실시간 편집·알림 묶음·올림 차액·공동 피드 공개 세부처럼 미정인 정책은 관련 구현 전에 합의한다.
