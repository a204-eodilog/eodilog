# Research: 동행 초대·관리·나가기

계획에서 정한 것과 그 근거다. API는 문서가 아니라 백엔드 코드(`EodiLog/src/main/java`, 2026-11-05 dev `e42e349`)에서 확인했다. 화면은 피그마 어디로그(파랑) S18·S19를 봤다.

## R1. 초대 링크를 기기에 남기기

- **결정**: 이 기기에서 만든 링크를 보안 저장소(`src/lib/secure-storage.ts`)의 키 하나 `eodilog.invites`에 JSON으로 남긴다. 모양은 `{ userId, links: { [tripId]: { url, expiresAt } } }`이다.
  - 읽을 때 `userId`가 지금 사용자와 다르거나 `expiresAt`이 지났으면 없는 것으로 본다.
  - 쓸 때마다 만료된 항목을 지운다.
  - 로그아웃(`session-store.clearSession`)하면 키를 통째로 지운다. 여행에서 빠지면(나가기·삭제, 내보내져 404를 받음) 그 여행 항목만 지운다(FR-033).
  - 화면에서는 TanStack Query로 읽는다(`['trips', tripId, 'invite']`). 저장소 쓰기와 캐시 갱신을 한 훅에서 함께 한다.
- **근거**:
  - 서버는 토큰 원문을 만들 때만 돌려주고 해시만 보관한다(`InvitationSecretResponse`). 그래서 다시 들어왔을 때 같은 링크를 보여 주려면 기기에 남겨야 한다(FR-003).
  - 링크를 가진 사람은 누구나 여행에 들어올 수 있으니, 로그인 토큰과 같은 보안 저장소에 둔다.
  - 여행 20개를 남겨도 수 KB라 키 하나로 충분하다. 안드로이드만 배포한다.
- **고려한 다른 안**:
  - 메모리에만 두기: 앱을 다시 켜면 링크가 사라져 FR-003을 못 지킨다.
  - MMKV: 설치는 돼 있지만 아직 아무도 쓰지 않는다. 새 네이티브 사용처를 만드는 위험에 비해 얻는 게 없다.
  - 여행마다 키 하나: 로그아웃할 때 지울 목록을 따로 들고 있어야 한다.
  - 화면에 들어올 때 링크가 없으면 자동으로 만들기: 다른 동행이 보낸 링크를 몰래 무효로 만든다. 명세 FR-002 위반이다.

## R2. 공유와 복사

- **결정**:
  - [카카오톡]은 React Native `Share.share({ message })`로 OS 공유 창을 연다. 문구는 `"{여행 이름}에 함께 가요\n{url}"`이다.
  - [링크 복사]는 `expo-clipboard`의 `setStringAsync(url)` 뒤에 `toast.success('링크를 복사했어요')`를 띄운다.
  - 공유 창을 닫거나 취소해도 오류로 보지 않는다.
- **근거**:
  - 팀 기술 스택(`docs/plan/frontend-tech-stack-2026-11-03.md`)이 "초대·정산·장소 공유: React Native Share (설치 없음)"로 정했다.
  - `expo-clipboard ~58.0.4`는 이미 설치돼 있다.
- **고려한 다른 안**: 카카오 공유 SDK. 네이티브 설정과 카카오 앱 키 등록이 필요하다. 이번 범위가 아니다.
- **남은 위험**: 링크가 `ieohaeng://invitations/{token}` 앱 주소 형식이다. 카카오톡이 이것을 누를 수 있는 링크로 보여 주지 않을 수 있다. 앱 이름·주소를 바꾸는 팀 작업(`eodilog`)에서 다룬다. 이 명세에서는 서버가 준 `url`을 그대로 쓴다.

## R3. 함께하는 사람 목록은 여행 응답에서

- **결정**: S18·S19는 `GET /trips/{tripId}`(이미 있는 `useTrip`)의 `members`를 쓴다. 따로 `GET /trips/{tripId}/members`를 부르지 않는다.
  - 방장은 `trip.ownerMemberId`로 정한다.
  - 나는 `members.find(m => m.user.id === me.id)`이다.
- **근거**:
  - 백엔드 `TripResponse`가 "members는 ACTIVE 멤버만 joinOrder 순"을 담는다. 버전(`version`)도 같은 응답에 있어서, 버전 확인에 쓸 값과 화면에 그린 값이 한 번에 맞는다.
  - S19를 열 때 요청이 1번이다.
- **고려한 다른 안**: `/members` 따로 받기. 두 응답의 시점이 달라 버전과 목록이 어긋날 수 있다. 나간 사람까지 받는 옵션은 경비 화면에만 필요하다.

## R4. 버전 충돌(409)과 권한 바뀜(403)

- **결정**: 수정·넘기기·내보내기·나가기·삭제는 화면에 그린 `trip.version`을 `expectedVersion`으로 보낸다. 실패는 순수 함수 `memberActionFailure(error)` 하나로 나눈다.

  | 서버 답 | 종류 | 앱이 하는 일 |
  | --- | --- | --- |
  | 409 `VERSION_CONFLICT` | `conflict` | 여행을 다시 받는다(`refetchQueries(tripKey)`를 기다린다). 그다음 "그 사이 여행이 바뀌었어요" 안내를 띄우고 최신 화면을 그린다. 자동으로 다시 보내지 않는다 |
  | 403 `FORBIDDEN` | `notOwner` | conflict와 같이 다시 받는다. 방장 버튼이 사라진 화면에 "방장만 할 수 있어요" 안내를 띄운다 |
  | 404 `MEMBER_NOT_FOUND` | `memberGone` | 내보내기에만 나오고, 버전이 같을 때만 온다(대상이 나갔으면 보통 409가 먼저). "이미 여행에 없는 동행이에요" 안내를 띄우고 여행을 다시 받는다 |
  | 404 `TRIP_NOT_FOUND` | `tripGone` | 나가기·삭제에서는 성공으로 본다(FR-032). 수정·넘기기·내보내기에서는 '볼 수 없는 여행' 화면이 된다 |
  | 그 밖·연결 끊김 | `error` | 입력과 선택은 그대로 두고 실패 안내를 띄운다. 사용자가 다시 누른다 |

- **근거**:
  - 백엔드는 `requireOwner`(403)를 버전 확인(409)보다 먼저 한다(`TripMemberService` 184·187행). 그래서 방장이 바뀐 뒤 누르면 403이 먼저 온다. 둘 다 "내가 본 화면이 낡았다"는 뜻이라 같은 처리로 묶는다.
  - 자동으로 다시 보내면 사용자가 모르는 새 상태(예: 이어받을 사람이 바뀜) 위에 실행된다. SC-005 위반이다.
- **고려한 다른 안**: 409면 새 버전으로 한 번 자동 재시도. 이어받을 사람·혼자 남음 여부가 바뀐 줄 모르고 나가게 돼서 받아들이지 않는다.

## R5. 성공 뒤 캐시와 이동

- **결정**:

  | 동작 | 서버 답 | 캐시 | 이동 |
  | --- | --- | --- | --- |
  | 정보 수정 `PATCH /trips/{id}` | `Trip` | `setQueryData(tripKey, trip)`, 목록 키 무효화 | S19에 남는다 |
  | 방장 넘기기 | `Trip` | 위와 같음 | 시트를 닫고 S19가 동행 화면으로 바뀐다 |
  | 내보내기 | 204 | `invalidateQueries(tripKey, exact)`, 목록 키 무효화 | S19에 남는다 |
  | 나가기·삭제 | 200/202 | 아래 '빠지기' | `router.replace('/trips')` |

  - 목록 키는 두 개다. `MY_TRIPS_KEY = ['trips','mine']`(여행 탭)과 `['me','trips']`(N4 내 여행 목록, 다른 팀원 화면)이다. 둘 다 무효화하는 `invalidateTripLists(queryClient)`를 `features/trip/hooks`에 둔다. 새 여행 만들기(`use-create-trip.ts`)도 이것을 쓰게 바꾼다. 지금은 N4 목록을 빠뜨린다.
  - **빠지기 순서**:
    1. `router.replace('/trips')`
    2. `cancelQueries` + `removeQueries({ queryKey: ['trips', tripId] })`
    3. 목록 키 무효화
    4. 기기의 초대 링크 지우기

    먼저 지우고 이동하면, 아직 떠 있는 상세·설정 화면이 다시 받아 404를 받는다. 그러면 '볼 수 없는 여행'이 번쩍인다.
  - `['trips', tripId]`를 앞에 둔 키는 여행·경비·정산·초대 링크 캐시를 모두 덮는다. 경비 기능의 `expenseKeys`가 이 앞자리를 쓴다.
- **근거**: 사용자 입력("성공하면 여행 상세·목록 캐시를 갱신", "나간 뒤나 삭제한 뒤에는 여행 목록으로 replace하고 그 여행의 캐시를 지운다"), FR-014·FR-028.

## R6. 여행 정보 수정은 [완료] 한 번으로

- **결정**: 피그마 S19처럼 머리줄 [완료]를 누르면 한 번에 저장한다. 고칠 동안의 값은 zustand 스토어 `useTripEditDraft`에 둔다. S19와 여행지 검색 화면이 함께 쓰므로, 새 여행의 `useNewTripDraft`와 같은 방식이다.
  - **채우기**: S19를 처음 열 때와 409 뒤에만 채운다. 채울 때의 여행 전체를 `base`로 기억한다. 수정 중에 앱이 다시 앞으로 와서 여행을 새로 받아도 다시 채우지 않는다. 그래야 고치던 값이 사라지지 않는다.
  - **버전**: 저장은 `base`와 비교하고 `expectedVersion = base.version`을 보낸다. 그 사이 다른 동행이 바꿨으면 저장할 때 409로 알게 된다. 캐시의 최신 버전을 보내면 앞사람의 변경을 모르고 덮어쓰게 된다(SC-003).
  - **본문**: 순수 함수 `buildTripUpdate(base, draft)`가 만든다.
    - 바뀐 칸만 담는다.
    - 기간을 비우면 `startDate: null, endDate: null`을 함께 보낸다.
    - 여행지를 모두 빼면 `destinationRegionIds: []`를 보낸다.
    - 이름은 앞뒤 공백을 지운다.
    - 바뀐 게 없으면 `null`을 돌려준다. 이때는 요청 없이 뒤로 간다.
  - **충돌(409)**: 최신 여행으로 스토어를 다시 채운다(`base`도 최신 여행이 된다). 명세 US2-6대로 "최신 값을 보여 주고 다시 고치게" 하는 것이다.
  - **실패**: 피그마 '저장 실패' 상태처럼 맨 위에 빨간 띠를 띄우고 입력값은 둔다.
  - **[뒤로]**: 고친 값을 버리고 나간다. 새 여행과 같이 화면이 닫힐 때 스토어를 비운다.
- **스토어 공통 조각**: 이름·기간·여행지 칸과 그 설정 함수(`setTitle`·`setRange`·`addRegion`·`removeRegion`)는 1번 `use-new-trip-draft.ts`에서 공통 조각 `tripDraftFields`로 뽑아 두 스토어가 함께 쓴다. 새 여행 스토어는 여기에 `reset`을, 수정 스토어는 `base`·`fill`·`reset`을 더한다.
- **여행지 검색 다시 쓰기**: `RegionSearchScreen`이 `draft?: 'new' | 'edit'`(기본 'new')를 받는다. 화면 안에서 두 스토어 훅을 언제나 둘 다 부르고 값으로 하나를 고른다. 훅을 속성으로 넘기거나 조건에 따라 부르면 훅 규칙과 React Compiler에 걸리기 때문이다. 설정용 주소 `trips/[tripId]/settings-region`은 `draft="edit"`로 내보낸다.
- **기간 시트**: `DateRangeSheet`를 그대로 쓴다. 기간을 비우는 것은 이미 된다(이전 명세 Edge Cases).
- **근거**: 피그마 S19 '동행이 볼 때'·'저장 실패'에 [완료]와 오류 띠가 있다. 서버 PATCH도 생략한 칸은 유지해서 바뀐 칸만 보내기에 맞다.
- **고려한 다른 안**: 칸마다 바로 저장. 요청이 칸 수만큼 생기고 버전 충돌도 그만큼 잦다. 피그마와도 다르다.

## R7. 방장 메뉴와 내보내기 방식

- **결정**: 피그마를 따른다. S19 아래 메뉴 줄은 순수 함수 `settingsActions(role, memberCount)`가 정한다.

  | 내 역할 | 메뉴 줄 (위에서부터) |
  | --- | --- |
  | 동행 | 여행에서 나가기 |
  | 방장 | 방장 넘기기 · 동행 내보내기 · 여행에서 나가기 · 여행 삭제(빨강) |

  - 방장이 혼자면 방장 넘기기·동행 내보내기는 누를 수 없다. 설명 "넘길 동행이 없어요"·"내보낼 동행이 없어요"를 붙인다(FR-020).
  - [방장 넘기기]와 [동행 내보내기]는 같은 하단 시트 `MemberPickSheet`를 연다. 나를 뺀 동행을 참여 순서로 보여 주고 하나를 고른다.
    - 넘기기: 피그마 '방장 넘기기 대상 선택'처럼 "{닉네임}님에게 넘기기" 버튼을 둔다.
    - 내보내기: 고른 뒤 `ConfirmSheet`로 한 번 더 묻는다.
  - 구성원은 피그마처럼 얼굴 줄로 보인다(공통 `AvatarGroup` 모양).
- **넘기기 확인**: 넘기기 시트의 버튼에 받을 사람 이름이, 설명에 넘긴 뒤 바뀌는 점이 있다. 그래서 확인창을 따로 두지 않는다(명세 FR-018).
- **나가기에서 연 넘기기**: 방장이 나가기 시트의 [다른 사람에게 넘기기]로 넘기면, 넘긴 뒤 나가기 시트(일반 동행용)를 다시 연다. 흐름도 5.2의 넘기기 → 나가기와 같다(명세 US3-4). S19 메뉴에서 연 넘기기는 다시 열지 않는다.
- **방장 표시**: S19 구성원 얼굴 줄에는 피그마대로 방장 표시가 없다. 방장 표시는 S18 목록에서 본다(명세 FR-019).
- **피그마 오류**: '저장 실패' 프레임은 동행 화면인데 [여행 삭제]가 보인다. 명세 FR-016을 따르고 동행에게는 보이지 않는다.
- **근거**: 화면 목록 S19 상태 3개가 피그마 프레임과 같다. 방장 넘기기 대상 선택은 S19 위 시트로 그려져 있다.

## R8. 이어받을 사람과 혼자 남음

- **결정**: 순수 함수 두 개를 둔다.
  - `nextOwner(trip, myMemberId)`: 나를 뺀 `members` 중 `joinOrder`가 가장 작은 사람. 없으면 `null`.
  - `isAlone(trip)`: `members.length === 1`.
  - `LeaveTripSheet`에 넘기는 값:
    - `nextOwnerName`: 내가 방장이고 혼자가 아닐 때만 넘긴다.
    - `alone`: `isAlone(trip)`.
    - `onHandOver`: 나가기 시트를 닫고 넘기기 시트를 연다.
- **근거**: 백엔드 나가기는 "남은 동행 중 참여 순이 가장 빠른 사람"을 방장으로 만든다(`TripMemberController.leave` 설명). 나갔다 다시 들어온 사람은 `joinOrder`를 새로(맨 뒤로) 받는다(`acceptInvitation`). 그래서 `joinedAt`이 아니라 `joinOrder`로 고른다.

## R9. 나가기 시트(S50)는 이미 있는 것을 쓰고 조금 고친다

- **결정**: B가 만든 `features/trip/components/leave-trip-sheet.tsx`(`b191c1f`·`c698645`, 이미 dev에 머지)와 `hooks/use-leave-trip.ts`를 쓴다. 임시 시트는 만들지 않는다. 다만 지금 시트는 사진·채팅 지우기를 `cleanupSupported` 하나로 함께 켜고 끈다. 명세(채팅은 고름, 사진은 숨김)와 맞지 않아 이렇게 바꾼다.
  - 사진 줄을 숨기는 `showPhotos`(기본 `false`)를 추가한다. 숨기면 `deleteOwnPhotos`는 언제나 `false`다.
  - 채팅 체크의 지원 여부를 따로 받는 `messageCleanupSupported`(기본 `true`)를 둔다. 서버가 이미 `deleteOwnMessages=true`를 받는다(`LEAVE_CLEANUP`, 202).
  - `cleanupSupported`는 위 둘로 대신하고 지운다. 다른 사용처는 부품 예시 화면 `src/app/dev/ui.tsx` 506행 하나라 함께 고친다.
  - `api.ts`의 `leaveTrip` 설명("메시지 지우기는 true면 400")을 서버에 맞게 고친다.
- **같이 할 일**: B(작성자 tpdms3048)에게 알리고, `docs/design/screens/S50-confirm.md`의 "곧 지원돼요" 줄(9·65행)을 고치도록 부탁한다.
- **근거**: 사용자 입력("B의 S50 시트를 쓰고 머지 전이면 임시 시트로 대신")에서 머지 전 경우는 해당 없다. 확인 시트 공통 부품 `ConfirmSheet`도 이미 있어서 내보내기·여행 삭제 확인에 쓴다.

## R10. 나가기·삭제 결과

- **결정**:
  - 나가기는 `useLeaveTrip`을 그대로 쓴다. 이 훅은 404를 `null`로 바꿔 성공으로 본다.
  - 안내 토스트:
    - `tripDeleted`면 "여행을 삭제했어요"
    - 아니면 "{여행 이름}에서 나왔어요"
  - 정리 작업(`cleanupJobId`)은 기다리지도 조회하지도 않는다(SC-007).
  - 여행 삭제: `DELETE /trips/{id}?expectedVersion=`가 202 `JobRef`를 준다. 404면 성공으로 본다. 그다음은 R5의 '빠지기'를 한다.
- **근거**: 백엔드 설명 "여행은 즉시 404가 되고 남은 자료는 작업이 지운다", FR-028·FR-032.

## R11. 만료 날짜와 '만료됨' 판단

- **결정**:
  - 만료 날짜 표시: `expiresAt`(UTC)을 서울 날짜로 바꿔 `"11.12(목)까지 쓸 수 있어요"`로 보인다. `src/lib/seoul-date.ts`의 날짜 표시를 쓴다. 피그마는 "10.30까지"인데, 다른 화면과 같게 요일을 붙인다.
  - 만료됐는지: 날짜가 아니라 시각으로 비교한다(`Date.now() >= Date.parse(expiresAt)`). S18을 열 때와 앱이 다시 앞으로 올 때 판단한다.
- **근거**: 서버는 만료 시각부터 참여를 막는다. 날짜로만 비교하면 마지막 날 몇 시간을 틀리게 보인다.
