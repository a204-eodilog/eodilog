# 백엔드 A/B 개발 분담 — 2026-11-06

오늘 개발할 범위에 대한 전달용 분담안이다. 백엔드 전체 잔여 작업 목록은 아니다. 현재 코드 기준으로 설정·알림 기반·초대 취소·채팅 실시간 전달·개인 즐겨찾기·여행 공동 장소 저장은 구현돼 있으므로 다시 배정하지 않는다.

## 오늘 분담

| 담당 | 작업 | 오늘 목표 |
| --- | --- | --- |
| A | 파일 업로드 공통 기반 + 여행 사진 등록·조회 | CAPTURE와 TRIP_PHOTO 업로드를 지원하고, 여행 사진은 배치 생성 → 업로드 → 등록 → 목록·다운로드까지 연결 |
| B | AI 준비물 추천·체크리스트 채택 | 추천 요청 → 비동기 작업 처리 → 결과 조회 → 선택 항목을 실제 체크리스트에 추가 |

두 작업은 독립적으로 진행한다. B는 A의 파일 업로드 구현을 기다릴 필요가 없다.

## A — 공통 파일 업로드와 여행 사진

### 구현 범위

- `POST /api/v1/assets/upload-intents`: 업로드 대상·소유자·용도와 업로드 방법 반환.
- `POST /api/v1/assets/{assetId}/complete`: 실제 객체 존재·크기·파일 형식 검사 후 `PENDING → READY` 전환.
- `DELETE /api/v1/assets/{assetId}`: 본인의 PENDING 업로드 취소 및 객체 정리. 취소 후 complete 거부.
- `GET /api/v1/assets/{assetId}/download`: 접근 권한 확인 후 파일 제공.
- assets 테이블·상태 관리·파일 저장소 연결 및 실패 처리.
- `POST /api/v1/trips/{tripId}/photo-upload-batches`: 1~50장 배치 생성.
- `POST /api/v1/trips/{tripId}/photos`: READY 파일을 여행 사진으로 등록.
- `GET /api/v1/trips/{tripId}/photos`: 여행 사진 목록 조회.

사용자 확정 범위는 **CAPTURE와 TRIP_PHOTO 둘 다**다. 공통 assets/S3 기반을 먼저 만들고, CAPTURE(JPG/PNG)와 여행 사진(JPG/PNG/HEIC)을 연결한다. CAPTURE는 소유자만 접근하며, 등록된 여행 사진은 해당 여행의 ACTIVE 멤버만 다운로드할 수 있다. 여행 사진은 소유자·여행·배치 일치와 배치 한도를 검사한다. PROFILE과 피드 경유 접근은 후속이다.

### 착수 전에 정할 것

- 사용할 파일 저장소와 개발 환경 설정.
- 용도별 파일 크기 제한, 업로드 유효 시간, 미완료 파일 정리 방식.
- HEIC 실제 형식 검증·변환 방식 및 사진의 비공개 촬영시각·위치 메타데이터 취급.
- 파일 업로드 방식 및 complete 검증·정리 실패의 응답 계약.
- 공개 제공 파일의 EXIF/GPS 제거 방식. 비공개 원본과 공개 제공 파일의 취급 범위를 구분한다.

### 완료 기준

- 정상 파일을 실제 저장소에 업로드하고 complete 후 다운로드할 수 있다.
- 타인의 complete·취소와 CAPTURE 다운로드를 차단한다. 여행 사진 다운로드는 ACTIVE 멤버 권한을 확인한다.
- 여행 사진 배치 생성 → 업로드 → 사진 등록 → 목록·다운로드가 동작한다.
- 같은 파일의 중복 등록과 다른 소유자·여행·배치 파일 등록을 차단하고, 동시 요청에도 배치 한도를 초과하지 않는다.
- 배치의 일부 파일이 실패해도 이미 성공한 사진은 유지한다.
- 크기·실제 형식 불일치와 존재하지 않는 객체를 READY로 만들지 않는다.
- 취소한 업로드는 다시 완료할 수 없고, READY 파일을 업로드 취소 API로 삭제할 수 없다.
- 관련 테스트, API 명세·Swagger 갱신, 백엔드 build 통과.

사진 수동 편집·삭제·그룹 관리·AI 분류·공동 피드는 후속이다. 여행 삭제 시 사진·파일 정리는 이번 사진 도입과 함께 기존 TRIP_DELETE 작업에 연결한다. CAPTURE를 이용한 AI 장소 추출 자체는 후속이다.

## B — AI 준비물 추천과 채택

### 현재 연결 지점

- AI 서버에는 준비물 추천 기능이 구현돼 있다(`ai/app/features/checklist_suggestion`).
- 백엔드에는 `jobs` 기반과 기본 체크리스트 CRUD가 있다.
- `ChecklistService`는 현재 `sourceJobId`·`suggestionIndex`를 보낸 AI 제안 채택 요청을 거부한다. 이 부분을 실제 결과 검증·채택으로 연결한다.
- `JobKind.CHECKLIST_SUGGESTIONS` enum 선언만으로 기능이 동작하는 것은 아니므로 핸들러·접근 정책·호출 API를 함께 연결한다.

### 구현 범위

1. 현재 API 명세 §6과 AI 요청·응답 모델을 확인해 준비물 추천 요청·결과 조회 계약을 맞춘다. 명세에 정의된 경로를 재사용한다.
2. 추천 요청 시 ACTIVE 여행 멤버 권한·입력·AI 기능 설정을 검사하고 작업을 등록한다.
3. 기존 jobs worker에 `CHECKLIST_SUGGESTIONS` 핸들러와 접근 정책을 연결한다.
4. AI 준비물 추천 API를 호출하고 성공 결과·실패 상태를 저장한다.
5. 결과를 조회하고, 선택한 제안을 기존 체크리스트 생성 API의 `sourceJobId + suggestionIndex`로 채택한다.

AI 서버 호출은 `X-Internal-Token`과 `X-Trace-Id`를 전달한다. 타임아웃은 AI 문서의 요청 예산과 맞추며, 내부 토큰·주소는 환경 설정으로 관리한다.

### 착수 전에 정할 것

- AI 요청에 필요한 여행 기간·목적지·기존 준비물 등의 입력 출처와 스냅샷 범위.
- 같은 제안의 중복 채택 판정 범위와 재요청 응답.
- 설정 OFF 및 작업 진행 중 설정 변경 시 처리. 자동 반영 기준이 정해지기 전에는 사용자가 선택해 채택하는 흐름을 우선한다.
- 실패·재시도·결과 조회 응답은 기존 jobs 계약을 재사용하고, 명세와 달라지는 부분은 먼저 공유한다.

### 완료 기준

- 추천 요청으로 JobRef를 받고 작업 상태와 추천 결과를 조회할 수 있다.
- 실제 AI 서버 호출을 한 번 이상 확인한다. 테스트 대체로만 검증한 경우 실제 연동 완료와 구분해 기록한다.
- 성공한 작업의 유효한 suggestionIndex만 채택할 수 있다.
- 다른 여행 작업·권한 없는 사용자·실패/진행 중 작업·잘못된 인덱스의 채택을 차단한다.
- 동일 제안을 재요청해도 준비물 항목이 중복 생성되지 않는다.
- AI 기능 OFF 상태를 검사하고, 외부 호출 실패가 무기한 진행 중으로 남지 않는다.
- 관련 테스트, API 명세·Swagger 갱신, 백엔드 build 통과.

## 작업 경계와 병합

| 영역 | 담당 |
| --- | --- |
| assets·사진 등록/조회·배치·파일 저장소 코드·마이그레이션 | A |
| checklist, 준비물 추천 핸들러·접근 정책, 필요한 AI 호출 코드 | B |
| 기존 jobs·설정 공통 코드 | 재사용 우선. 변경 필요 시 상대에게 범위 공유 |
| build.gradle·application 설정·API 명세 등 공통 파일 | 각자 필요한 부분만 수정하고 병합 순서 공유 |

- 최신 `origin/dev`에서 각자 별도 작업 브랜치를 만들고 MR 대상은 `dev`로 한다. 현재 로컬 통합 브랜치를 작업 기준으로 삼지 않는다.
- Jira 키는 실제 발급된 키를 사용한다. 이 문서에서는 새 키를 임의 지정하지 않는다.
- Flyway는 새 마이그레이션으로 추가하고 기존 병합 파일은 수정하지 않는다. 병합 직전 버전 순서를 확인한다.
- 각자 `.\gradlew.bat build`를 통과시키고, 프론트 담당자에게 요청·응답 예시와 오류 코드를 전달한다.
- 사진 편집·그룹 관리·AI 분류, 장소 추출·피드·소셜·추천/코스 AI 연동은 후속 작업으로 분리한다.
