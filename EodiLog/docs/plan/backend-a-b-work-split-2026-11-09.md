# 다음 백엔드 A/B 개발 분담 — 2026-11-09

로컬 dev `8957234`의 실제 구현과 API 명세를 기준으로 정리한 다음 작업 분담이다. 착수 전 최신 origin/dev에서 중복 구현 여부를 다시 확인한다.

## 분담

| 담당 | 이번 작업 | 사용자에게 제공할 흐름 |
| --- | --- | --- |
| A | 여행 사진 수동 편집·개별 삭제·요약 | 올린 사진의 장소/주제를 보정하고, 사진을 삭제하고, 분류별 건수를 확인 |
| B | URL·캡처 기반 AI 장소 추출 | 링크/캡처 입력 → 추출 작업 → 후보 조회 → 사용자가 고른 장소 저장 |

이전 작업의 파일 업로드·사진 배치/등록/목록과 AI 준비물 추천/채택은 재배정하지 않는다. 두 작업은 독립 진행한다.

### A 구현 반영

2026-11-09: 사진 PATCH·개별 DELETE·photo-summary와 실제 topic 필터를 구현했다. 편집·삭제는 ACTIVE 멤버인 업로더만 가능하며 주제는 LANDSCAPE/FOOD/PEOPLE/OTHER 중 중복 없는 0~4개다. 삭제는 즉시 숨긴 뒤 PHOTO_DELETE로 파일을 정리하고, 재시도 소진 후에도 정기 정리가 파일 삭제를 계속 시도한다. B의 장소 추출 구현은 이 문서에서 완료로 간주하지 않는다. 상세 계약은 [API 명세](../../../docs/api-spec.md) §7을 따른다.

실제 S3 검증도 완료했다. `AssetRealS3Test` 3개 성공: 업로드·다운로드, 서명 Content-Type/업로드 취소, 여행 사진 삭제 API → worker 성공 → 원본·표시 객체 부재 확인. 검증용으로 새로 올린 파일만 사용했고 `.env`는 변경하지 않았다.

A 작업 Jira: [EODI-226](https://jira.example.com/browse/EODI-226). 작업 브랜치: `feature/EODI-226-photo-management`.

## A — 여행 사진 관리

### 범위와 순서

1. `PATCH /api/v1/trips/{tripId}/photos/{photoId}`: 장소·주제 수동 보정과 expectedVersion 검증. 필드 생략과 null의 의미를 구분한다. 수동 보정 이력을 남겨 이후 AI가 덮어쓰지 않도록 한다.
2. `DELETE /api/v1/trips/{tripId}/photos/{photoId}`: 삭제 요청 직후 목록·다운로드에서 제외하고, 기존 jobs 기반의 PHOTO_DELETE 작업으로 원본·표시 객체를 정리한다.
3. `GET /api/v1/trips/{tripId}/photo-summary`: 필터와 독립적인 전체·주제/장소별 건수·미지정 수를 제공한다. 기존 목록의 topic 필터를 실제 데이터와 연결한다.

### 구현 전 고정할 계약

- 편집·삭제 권한은 명세의 업로더 제안을 기본으로 하되 ACTIVE 여행 멤버 조건도 유지한다. 이는 이번 분담의 제안이며 확정된 기존 정책으로 취급하지 않는다.
- 주제 허용값·개수, 장소 유효성, version 충돌 응답을 API 명세·Swagger와 맞춘다.
- groupId는 그룹 관리 계약이 마련되기 전 임의로 구현하지 않는다. 이번 PATCH의 그룹 변경 지원 범위를 명세에 명시한다.
- 이미 삭제 중인 사진 재요청과 완료된 사진 재요청의 응답을 정한다. 파일 삭제 실패는 재시도하고 사진을 다시 노출하지 않는다.

### 완료 기준

- 본인 사진 수정 성공, 타인/이탈자 접근 차단, 오래된 version 충돌을 검증한다.
- 삭제 요청과 다운로드가 경합해도 새 요청은 삭제 사진을 제공하지 않는다. 이미 시작한 스트림의 처리 범위는 문서화한다.
- S3 삭제 실패 후 재시도, 중복 실행, 여행 전체 삭제와의 경합을 검증한다.
- 요약과 필터 결과가 실제 사진 변경·삭제를 반영한다.
- 관련 테스트·API 명세·Swagger를 갱신하고 백엔드 build를 통과시킨다.

사진 이동·일괄 변경·그룹 관리·AI 사진 분류·피드 공개는 다음 작업이다. 이번에 모두 묶지 않는다.

## B — AI 장소 추출

### 범위와 순서

1. `POST /api/v1/extractions`: URL 또는 captureAssetIds를 받아 PLACE_EXTRACTION 작업을 만든다. 캡처는 최대 10장이고, 본인 소유 READY CAPTURE(JPG/PNG)만 허용한다.
2. 기존 jobs worker에 핸들러·작업 소유자 접근 정책을 연결한다. CHECKLIST_SUGGESTIONS의 구현을 참고하고 공통 worker를 중복 작성하지 않는다.
3. AI 서버 `POST /ai/v1/place-extractions`에 multipart로 URL·메모·허용된 캡처 바이트를 전달한다. X-Internal-Token·X-Trace-Id와 기존 호출 예산을 따른다.
4. `GET /api/v1/extractions/{jobId}`: 본인 작업의 상태/결과 계약을 명세에 맞춰 제공한다. AI 공급자 장소는 기존 장소 resolver/upsert를 재사용해 로컬 장소 ID로 연결한다.
5. `DELETE /api/v1/extractions/{jobId}`: 작업 취소·입력/후보 제거를 처리한다. 삭제 뒤 늦게 도착한 AI 결과가 다시 노출되지 않도록 한다.
6. 선택한 후보는 기존 개인 북마크·여행 공동 장소 저장 API로 저장한다. 추출 성공만으로 자동 저장하거나 방문 기록을 만들지 않는다.

### 구현 전 고정할 계약

- 일반 작업 조회와 추출 전용 GET의 역할, 진행 중 응답, 실패/취소 응답을 API 명세 및 기존 jobs 계약과 맞춘다.
- 캡처 바이트는 기존 assets/ObjectStorage를 통해 읽는다. 공개 S3 URL이나 새 업로드 API를 만들지 않는다. 공통 클라이언트의 multipart 지원이 필요하면 B가 추가한다.
- 캡처 사용 중 정리 작업과의 경합, 추출 삭제 시 입력 보존/제거 범위와 재사용 참조 정책을 정한다. 북마크·장소·다른 자료가 참조하는 객체까지 무조건 삭제하지 않는다.
- 후보 ID·로컬 place ID·place 없는 후보의 수동 보정 흐름을 명세의 ExtractionResult와 맞춘다. 입력 URL 지원 범위·용량 등 미정 정책을 임의 확정하지 않는다.

### 완료 기준

- URL만/캡처만/함께 입력한 정상 요청을 검증한다. 실제 AI 서버 연동 여부는 대체 테스트와 구분해 기록한다.
- 타인의 캡처·PENDING·다른 용도 파일과 11장 이상 입력을 차단한다.
- 후보 다수·장소 없음·일부 자료 실패·AI 장애/타임아웃을 처리하고 작업이 무기한 진행 상태로 남지 않는다.
- 타인 작업 조회/삭제를 차단하고 삭제와 완료 경합에도 입력·결과가 복원되지 않는다.
- 선택한 후보로 기존 저장 API를 호출하는 예시를 프론트에 전달한다.
- 관련 테스트·API 명세·Swagger를 갱신하고 백엔드 build를 통과시킨다.

## 작업 경계와 병합

| 영역 | 담당 |
| --- | --- |
| photo 편집/삭제/요약, PHOTO_DELETE 핸들러·접근 정책 | A |
| extraction API/저장, PLACE_EXTRACTION 핸들러·접근 정책, AI multipart 호출 | B |
| assets·ObjectStorage | 기존 구현 재사용. 변경 필요 시 수정 파일과 계약을 공유 |
| jobs 공통·설정·의존성·API 명세·ERD | 각자 필요한 부분만 수정하고 겹치는 변경은 병합 순서를 공유 |

- 최신 origin/dev에서 각자 Jira 키를 포함한 별도 브랜치를 만들고 dev 대상으로 MR을 연다. 실제 Jira 키는 발급 후 기입한다.
- 기존 Flyway 파일은 수정하지 않고 새 마이그레이션을 추가한다. 병합 시 버전 순서를 확인한다.
- 전체 백엔드 완료를 의미하는 분담은 아니다. 이후 사진 AI 분류·그룹, 코스/여행 추천 AI, 공동 피드·지도·타임라인 등의 후속 범위를 별도로 나눈다.
